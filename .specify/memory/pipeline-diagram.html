App Data Analysis Pipeline

How a spectrum or hyperspectral map moves through the bundled Shiny app (inst/shiny/), from upload to every rendered plot, table, and download. Boxes are colored by role — input, function, decision, user-triggered recompute, output — diamonds mark every point where data shape or a user setting sends processing down a materially different function path, dotted rose lines tap each output back to every upstream point that actually decides whether it exists or what shape it takes, and dashed teal lines show click-driven interaction between outputs (e.g. the Heatmap driving the Spectrum Plot). Hover or focus any box for the exact reactive/function name, source location, and any nuance the short label can't carry.

Constitution Principle X (Data Analysis Pipeline Fidelity): this diagram is the canonical map of the app's analysis pipeline. Deviations from it (new stages, changed branch conditions, new/removed function calls, or a changed output dependency) must not happen incidentally — they must be an explicit part of a plan, and that plan must name the diagram box(es)/decision(s) it changes and update this file. See .specify/memory/constitution.md.

Uploaded File(s)
Single .rds files are restored directly with as_OpenSpecy(); every other supported format goes through read_any(). Multiple files/members are combined next. server.R:222-359
Read & Combine

Output becomes preprocessed$data, the single upload-level object everything else reads from. Runs immediately on upload, live, regardless of Run. server.R:222-359 · R/read_multi.R:45 · R/manage_spec.R:44
Passes validity check?
check_OpenSpecy()
Verifies wavenumber/spectra/metadata shape and coherence. Still part of the live upload handler, not gated by Run — it has to pass before Click Run (below) even becomes reachable. server.R:301 · R/as_OpenSpecy.R:469
Upload Error (abort)
show_alert + upload_status_state fire; preprocessed$data is never set, so no later stage runs at all. server.R:301-343
▶ Click Run
input$run_analysis. Positioned here because nothing downstream produces a visible result without it: XY Grid Normalize onward is either literally inside canonical_state_gate's Run-triggered closure, or — like data()/spatial_data() themselves — is technically a live reactive() that Shiny only evaluates because canonical_state_gate (or the narrow click-driven raw-spectrum/click-position paths) asks for its value. Change a setting: nothing visible updates. Click Run: the whole cascade below executes, and every scientific output derives from that one snapshot (see "Build canonical_state" further down). Also fires the dependent Run-gated caches (Quantification, Pixel Projection, AI Model Classification) on the same click, in priority order (RESET, then CANONICAL, then DEFAULT). server.R:75-106, 1296
↻ Recalculate Preview
input$recalculate_snr. Unlike Click Run (above), this does NOT gate the analysis pipeline — it only refills the Signal/Noise histogram preview (snr_preview()) from the already-live signal_to_noise() metric, so thresholds can be previewed without committing to a full Run. Its card dims ("stale") whenever a setting it depends on has changed since the last recompute. server.R:1080-1099
XY Grid Normalize
gen_grid() · optional
Only runs if "Snap to grid" is on AND coordinates are spatially discontinuous; rewrites metadata$x/$y. Spectra values are untouched. server.R:440-451 · R/as_OpenSpecy.R:541
Map data?
ncol(spectra) > 1
A single uploaded spectrum always takes the "no" path below — Spatial Smooth and Collapse become no-ops regardless of switch position, checked the same way at every stage that depends on pixel count. server.R:732, 1109-1114
Spatial Smooth
spatial_smooth() · optional, map only
A plain live reactive, not gated by Run: technically it recomputes on the next read after Spatial Smooth/sigma changes, not on a fixed schedule. Runs only if the switch is on; convolves each pixel with its spatial neighbors. The result (spatial_data()) is what Signal/Noise, Collapse, and Pixel Projection all read from next — not the raw upload. Only Run-gated/click-triggered code reads it, so the actual convolution never executes before Run: current_select_xy() (the always-on marker-position sync) previously read spatial_data()$metadata purely for x/y coordinates, which spatial_smooth() never changes, and that forced the real computation live on every toggle; fixed by reading data() (pre-smoothing, identical metadata) there instead. server.R:727-743 · R/spatial_smooth.R:28
Memory preflight safe?
.app_memory_preflight()
Live reactive, estimated from preprocessed$data's dimensions; drives the advisory pre-Run status text AND is re-checked inside canonical_state_gate at Run time as a safety gate. server.R:1253-1283, 1313-1320
Analysis Blocked
canonical_state_gate short-circuits to an empty/diagnostic result before spatial_data() is ever computed. server.R:1313-1320
Signal/Noise Compute
sig_noise() · live, not Run-gated
A plain live reactive (deliberately cheap): recomputes immediately on any relevant setting change, before Run. signal_to_noise_basis() picks spatial_data() ("Raw/Spatially Smoothed", default) or ordinary_process(spatial_data()) ("Fully Processed") per the Signal/Noise Basis control; sig_noise(basis, step=10) yields the per-pixel metric. signal_eligible() masks it by MinSNR()/MaxSNR() (-Inf/Inf, i.e. no-op, when the threshold switch is off). Only the S/N Histogram *preview* is deliberately held back (Click Run or Recalculate Preview, both above) to avoid flicker — the underlying metric itself is always current. server.R:1028-1053 · R/sig_noise.R:59
Collapse particles?
input$collapse_decision
particle_pipeline_enabled(): true only if the switch is on AND the upload has >1 pixel. Signal/Noise threshold gating (above) applies on BOTH branches, not just this one — a rejected pixel flat-lines either way. server.R:1109-1115
Ordinary Process
process_spec() + corrections
canonical_state_gate's !collapse branch: optional correct_spike() (residual method) and saturation check, then process_spec(adj_intens, conform_spec, subtr_baseline, smooth_intens, make_rel), then optional flatten_range()/restrict_range(). This exact sequence is reused at every "Ordinary Process" box in this diagram, and is the ONLY step that changes spectra values themselves — every later step (collapse, identification, quantification) only adds columns or picks which units exist. server.R:1357-1366, 457-725 · R/process_spec.R
Identity Pixel Mapping
identity_pixel_mapping()
R7 fix: even with Collapse off, a pixel failing the Signal/Noise threshold gets eligible=FALSE / unit_index=NA here, so it flat-lines on click instead of silently staying included. server.R:1363
Particle ID Strategy?
input$particle_id_strategy
All three strategies are backed by OpenSpecy:::.partition_particle_map(), just with different strategy= arguments and pre/post steps — see each box below. server.R:1328-1329, 1495 onward · R/automate_particle_analysis.R:608
Connected Threshold Regions
strategy = "collapse"
Without Correlation Threshold: .partition_particle_map(eligible=signal_keep, strategy="collapse") flood-fills spatially-connected same-eligibility pixels into particles, then Ordinary Process + (if identification is on) Library Identification run once on the collapsed units. WITH Correlation Threshold on: identification runs FIRST per-pixel, then partitioning re-runs with eligible = signal_keep & correlation_keep and material = the per-pixel match, so a region must also share a passing, matching material; a final Ordinary Process + app_aggregate_unit_matches() re-aggregates identification onto the final particles. Needs a real (non-model) library only when Correlation Threshold is on, else blocked with an "unavailable()" diagnostic. server.R:1495-1563, 1349-1354
Spatial Clusters
strategy = "partial_collapse"
Shares Non-spatial Clusters' first pass (PCA + k-means, dotted rose line), then takes the cluster-identified material labels and runs a SECOND .partition_particle_map(strategy="collapse", material=<cluster material>) to spatially merge same-material connected pixels into fewer, larger particles; re-processes and re-aggregates matches. Requires a real (non-model) library. Confirmed genuine divergence from Non-spatial Clusters on a real multi-particle map: 1 merged particle vs. 4. server.R:1453-1492
Non-spatial Clusters
strategy = "nonspatial_collapse"
.partition_particle_map(signal_subset, strategy="nonspatial_collapse", pca_components=, centers=, collapse_function=) clusters SPECTRA by PCA + k-means (not spatial position) into analysis_units = cluster-mean spectra, then Ordinary Process + Library Identification + Attach Best Matches run on the clusters. Stops here — no spatial merge step, unlike Spatial Clusters (dotted rose line: they share the clustering step above). server.R:1378-1451
Run library identification?
identification_active & lib_type != "model"
Combines the Identification on/off switch (default on) with lib_type != "model". Off: identify_blockwise() is never called; matches/pixel_matches stay NULL, so the Top Matches Table, match-based map colors, and Correlation Threshold (which needs identification) all become empty/unavailable. The AI Model Classification box further down has its own identical active-switch check and reaches several of the same outputs through a completely different path (ai_output()), NOT through matches/pixel_matches. server.R:1324-1325 · ui.R:205-208
Correlation Threshold on?
input$cor_threshold_decision
Requires identification to be on (UI note). Captured into run_settings$correlation_active alongside identification_active at the very start of canonical_state_gate, and feeds MinCor() (else -Inf, i.e. no-op). Gates the per-pixel correlation_keep mask used inside "Connected Threshold Regions" and "Spatial Clusters", and separately gates the Correlation Histogram and the correlation-based rejection shown on the Heatmap/Map Color Choices/Progress Bars. server.R:1015-1017, 1309-1310, 1495-1563
Library Identification
identify_blockwise / .match_spec_blockwise
identify_blockwise(object) calls OpenSpecy:::.match_spec_blockwise(object, reference, top_n=, block_size=1000L, type="roll"). Reference resolved by app_reference_for_query(library_filtered(), object). Inside "Connected Threshold Regions + Correlation Threshold" this can run twice — see that box. This path (and Attach Best Matches below it) is what feeds max_cor()/matches_to_single() in real-library mode; AI Model Classification feeds the exact same downstream functions through ai_output() instead when lib_type="model". server.R:1141-1160 · R/match_spec.R:213
Attach Best Matches
attach_best_matches / match_material
Adds max_cor_name, max_cor_val, material_class to object$metadata from best_match_rows(matches) + match_material(). Result becomes canonical_state()$object. server.R:1162-1194
Build canonical_state
canonical_state_gate · Run-gated
The single expensive-analysis owner: bundles object, matches, pixel_matches, pixel_to_unit, partition, error, diagnostic, and a run_settings snapshot (collapse/strategy/thresholds captured once per Run) so every downstream reader sees exactly what produced this result, never live inputs. This closure is exactly what Click Run (near the top of this diagram) executes. server.R:1296-1366+
canonical_final() / DataR()
validated read of canonical_state
validate()-guards on analysis_needs_reset() (new upload not yet Run) and a non-NULL object, else surfaces diagnostic/error text. DataR() is a compatibility alias. Per the Constitution's Bundled Shiny Application Boundary: every visible/exported result for one analysis state MUST derive from this one object. server.R:1634-1645, 1674
Quantification defined?
ratio_definitions() / measurement_definitions()
Purely data-driven, no switch: true if the user has added any peak-ratio or point-intensity definitions. Also Run-gated (quantified_data_gate), so it recomputes on the same Click Run event as canonical_state_gate, not independently. server.R:1676-1694
Quantification
app_attach_quantification()
Calls peak_ratio()/app_area_ratio() and point_intensity()/app_area_measurement() per user-defined row, adding numeric metadata columns only — never touches $spectra values. Its output (quantified_data()) is NOT a dead end: it feeds Download: Processed Spectra and Download: Top Matches directly (dotted rose lines), since both read quantified_data() rather than canonical_final() directly. Note: the package's quantify_particles() export is not used by the app. global.R:1374-1428
Pixel Projection
pixel_projection_gate · map only, Run-gated
Projects unit-level results (canonical_state()$object/$matches/$pixel_to_unit) back onto every raw pixel of spatial_data() for heatmap coloring; computes rejected/rejection_reason per pixel from Signal/Noise + correlation thresholds via app_threshold_rejection_mask(). server.R:2150-2220
Library type = model (AI)?
input$lib_type == "model"
Architecturally separate from Library Identification above — this path runs after canonicalization, not inside canonical_state_gate. It also disables filter/organism library controls and blocks strategies that need a real reference library. server.R:1324-1325, 1349-1354 · ui.R:228-241
AI Model Classification
ai_output_gate: match_spec()
Calls match_spec(data, library=libraryR(), na.rm=TRUE) directly on the already-finalized DataR() — bypasses identify_blockwise()/.match_spec_blockwise() entirely, and never populates matches/pixel_matches. Not a dead end: ai_output() feeds max_cor()/max_cor_identity() directly (server.R:1922-1941), which in turn feed the Heatmap's material coloring, Selection Metadata Table, and both Top Matches outputs (table + download) and Download: Thresholded Particles (dotted rose lines) — confirmed by reading each consumer's source. Spec 015 fixed the Top Matches Table specifically, which used to stay empty in this mode despite the others already showing AI results. server.R:1893-1914

Heatmap

output$heatmapA reads current_heatmap_data() ← pixel_projection(). Clicking the Heatmap is itself the trigger for the Spectrum Plot and Selection Metadata Table (dashed teal lines above) — those two do not feed back into it. server.R:2523, 2475
